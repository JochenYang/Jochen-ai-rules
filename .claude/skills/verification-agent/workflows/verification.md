# 验证工作流

## 验证原则
- 质疑假设：不盲目接受
- 证据驱动：要求证据支持
- 多角度验证：从不同角度检查
- 防止过度自信：识别不确定性

## 质疑技巧

### 苏格拉底式提问
- "为什么这样设计？"
- "有没有考虑其他方案？"
- "这个假设的依据是什么？"
- "如果这个假设不成立会怎样？"

### 反向思考
- "什么情况下会失败？"
- "最坏的情况是什么？"
- "有哪些隐藏的风险？"
- "如何证明这是错的？"

### 边界探索
- "极端情况下会怎样？"
- "边界条件是什么？"
- "性能上限在哪里？"
- "什么时候会崩溃？"

---

## 常见过度自信模式

### 技术过度自信
- ❌ "这个方案肯定是最优的"
- ✅ "这个方案在当前约束下较优，但有以下权衡..."

### 性能过度自信
- ❌ "性能绝对没问题"
- ✅ "基于测试数据，性能满足要求，但需要监控..."

### 安全过度自信
- ❌ "这样做完全安全"
- ✅ "已实施常见安全措施，但仍需定期审计..."

### 时间过度自信
- ❌ "肯定能按时完成"
- ✅ "预计 X 天完成，但可能因 Y 因素延期..."

## 输出格式

### 验证报告

```markdown
## 验证报告

### 总体评估
- 准确性：✅ 通过 / ⚠️ 需改进 / ❌ 严重问题
- 完整性：✅ 通过 / ⚠️ 需改进 / ❌ 严重问题
- 一致性：✅ 通过 / ⚠️ 需改进 / ❌ 严重问题
- 可行性：✅ 通过 / ⚠️ 需改进 / ❌ 严重问题

### 发现的问题

#### 🚨 严重问题
1. **安全漏洞** (文件: auth.ts, 行: 42)
   - 问题：密码未加密存储
   - 风险：数据泄露
   - 建议：使用 bcrypt 加密

#### ⚠️ 需要改进
1. **性能问题** (文件: api.ts, 行: 28)
   - 问题：N+1 查询
   - 影响：响应时间过长
   - 建议：使用 JOIN 或数据加载器

#### 💡 建议
1. **代码质量** (文件: utils.ts, 行: 15)
   - 问题：函数过长
   - 建议：拆分为多个小函数

### 未验证的假设
1. 假设数据库连接池大小足够（需要负载测试验证）
2. 假设第三方 API 可用性 99.9%（需要监控验证）

### 风险评估
- 技术风险：中等（依赖第三方服务）
- 业务风险：低（需求明确）
- 运维风险：中等（需要完善监控）

### 建议行动
1. 修复严重安全问题
2. 进行负载测试验证性能
3. 完善监控和告警
4. 补充缺失的测试用例
```
