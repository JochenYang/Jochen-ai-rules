# 代码审查工作流

## 阶段 1: 快速扫描（1-2分钟）

### 文件结构检查
- [ ] 文件命名符合项目规范
- [ ] 目录结构合理，职责清晰
- [ ] 导入语句组织良好（第三方库 → 内部模块 → 相对路径）

### 明显问题扫描
- [ ] 硬编码密钥、API密钥、敏感信息
- [ ] SQL注入风险（字符串拼接查询）
- [ ] XSS风险（未转义的用户输入）
- [ ] 明显的代码异味（重复代码、过长函数 > 50行）

---

## 阶段 2: 深度审查（5-10分钟）

### 代码质量

#### 函数设计
- [ ] 函数职责单一（SRP原则）
- [ ] 函数长度合理（< 50行为佳）
- [ ] 参数数量合理（< 5个为佳）
- [ ] 函数命名清晰表达意图

#### 变量命名
- [ ] 变量名清晰表达含义
- [ ] 避免单字母变量（除循环索引）
- [ ] 布尔变量使用 is/has/should 前缀
- [ ] 常量使用 UPPER_SNAKE_CASE

#### 错误处理
- [ ] 所有异步操作有错误处理
- [ ] 错误信息清晰有用
- [ ] 避免空 catch 块
- [ ] 关键操作有日志记录

#### 测试覆盖
- [ ] 核心逻辑有单元测试
- [ ] 测试覆盖率 > 80%
- [ ] 边界情况有测试
- [ ] 错误场景有测试

---

### 安全检查

#### 输入验证
- [ ] 所有用户输入经过验证
- [ ] 使用白名单而非黑名单
- [ ] 数据类型验证（字符串、数字、邮箱等）
- [ ] 长度限制和范围检查

#### 认证授权
- [ ] API端点有认证保护
- [ ] 权限检查在业务逻辑前
- [ ] 避免硬编码凭据
- [ ] Session/Token 安全管理

#### 敏感数据处理
- [ ] 密码使用安全哈希（bcrypt/argon2）
- [ ] 敏感数据加密存储
- [ ] 日志中不包含敏感信息
- [ ] HTTPS传输敏感数据

#### 依赖安全
- [ ] 依赖版本无已知漏洞
- [ ] 使用 npm audit / yarn audit 检查
- [ ] 避免使用废弃的包
- [ ] 定期更新依赖

---

### 性能分析

#### 算法复杂度
- [ ] 避免嵌套循环（O(n²) 或更高）
- [ ] 使用合适的数据结构（Map/Set vs Array）
- [ ] 避免不必要的计算
- [ ] 考虑缓存重复计算结果

#### 数据库查询
- [ ] 避免 N+1 查询问题
- [ ] 使用索引优化查询
- [ ] 分页处理大数据集
- [ ] 避免 SELECT *，只查询需要的字段

#### API性能
- [ ] 响应时间 < 200ms（理想）
- [ ] 使用缓存策略（Redis/内存缓存）
- [ ] 压缩响应数据（gzip）
- [ ] 实现限流防止滥用

#### 资源管理
- [ ] 及时关闭文件/连接
- [ ] 避免内存泄漏（事件监听器清理）
- [ ] 大文件使用流处理
- [ ] 避免全局变量污染

---

### 配置审查（重点）

#### 魔法数字检测
- [ ] 配置值有明确注释说明依据
- [ ] 关键配置有负载测试证据
- [ ] 避免随意设置的"看起来合理"的值
- [ ] 配置值可通过环境变量调整

#### 连接池设置
- [ ] 连接池大小基于实际负载测试
- [ ] 超时配置合理（连接超时、读写超时）
- [ ] 空闲连接清理策略
- [ ] 最大连接数限制

#### 超时配置
- [ ] 请求超时设置（防止长时间挂起）
- [ ] 连接超时设置（防止连接泄漏）
- [ ] 读写超时设置（防止慢查询）
- [ ] 超时值基于实际测量而非猜测

#### 资源限制
- [ ] 内存限制配置（防止OOM）
- [ ] 缓存大小限制（防止内存溢出）
- [ ] 线程池/进程池大小合理
- [ ] 文件上传大小限制

#### 安全配置
- [ ] 生产环境禁用调试模式
- [ ] 避免通配符CORS白名单
- [ ] Session超时时间合理（< 24小时）
- [ ] 密钥轮换策略

## 阶段 3: 输出报告

### 报告格式

按严重程度分类：

#### 🚨 关键问题（必须修复）
- 安全漏洞（SQL注入、XSS、硬编码密钥）
- 可能导致系统故障的配置（连接池、超时）
- 数据丢失风险
- 严重性能问题

#### ⚠️ 高优先级（应该修复）
- 性能降级风险
- 可维护性问题
- 缺少错误处理
- 测试覆盖不足

#### 💡 建议改进（可选）
- 代码风格改进
- 优化机会
- 额外测试覆盖
- 文档完善

### 示例输出

```markdown
## 审查结果

### 🚨 关键问题

1. **硬编码API密钥** (文件: `src/api/client.ts`, 行: 15)
   - 问题：API密钥直接写在代码中
   - 风险：密钥泄露，安全漏洞
   - 建议：使用环境变量 `process.env.API_KEY`

2. **SQL注入风险** (文件: `src/db/users.ts`, 行: 42)
   - 问题：使用字符串拼接构建SQL查询
   - 风险：SQL注入攻击
   - 建议：使用参数化查询或ORM

### ⚠️ 高优先级

1. **缺少错误处理** (文件: `src/services/payment.ts`, 行: 28)
   - 问题：异步操作没有try-catch
   - 风险：未捕获的异常导致服务崩溃
   - 建议：添加错误处理和日志记录

### 💡 建议改进

1. **函数过长** (文件: `src/utils/helpers.ts`, 行: 10-85)
   - 问题：函数长度75行，职责不单一
   - 建议：拆分为多个小函数，提高可读性
```

## 配置变更特别警示

⚠️ **那些"只是改变数字"的配置变更往往是最危险的。**

### 常见配置故障案例

1. **连接池过小** → 高并发时连接耗尽，服务不可用
2. **超时过长** → 慢查询堆积，资源耗尽
3. **超时过短** → 正常请求被中断，用户体验差
4. **缓存过大** → 内存溢出，OOM崩溃
5. **Session超时过长** → 安全风险，资源浪费

### 配置变更检查清单

- [ ] 配置值有明确的测试依据（负载测试报告）
- [ ] 有回滚计划（配置错误如何快速恢复）
- [ ] 有监控指标（如何验证配置是否有效）
- [ ] 考虑依赖关系（此配置影响哪些其他系统）
- [ ] 查看历史背景（为什么之前是这个值）

**成为防止配置故障的守护者。**
