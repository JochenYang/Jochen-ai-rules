# Development Loop

**RULE TYPE**: Mandatory workflow for non-trivial development tasks.

## 核心原则

使用按风险调节的开发循环：

1. 明确交付主张、范围、非目标和成功标准。
2. 读取足以区分根因的最小代码、约束和调用链。
3. 对非显然问题提出可证伪的根因或设计假设。
4. 执行假设为假时最可能失败的最短检查。
5. 选择正确、可维护、可验证且范围最小的方案。
6. 实施时不扩展需求、不顺手重构、不增加当前不需要的抽象。
7. 验证原始交付主张、关键正常路径和失败路径。
8. 基于实际代码、diff、日志和测试做一次自我审查。
9. 交付已验证项、未验证项、残余风险和最短下一步。

不要暴露内部链式思维。面向用户只报告结论、证据、关键取舍、必要假设和残余风险。

## 风险调节

### 低风险

适用于明确、局部、可逆且不改变关键行为的修改：

- 读取目标位置和适用约束；
- 完成聚焦修改；
- 检查 diff；
- 执行最短相关验证。

过程和交付保持简洁，不执行形式化流程表演。

### 中风险

适用于普通 bugfix、行为修改和沿用现有模式的功能开发：

- 优先复现或隔离当前行为；
- 提出可证伪假设并执行最短证伪检查；
- 实施最小正确修复；
- 验证变化行为、回归路径和关键失败路径；
- 完成一次基于证据的自我审查。

### 高风险

适用于架构、新技术栈、认证与权限、并发与事务、迁移、生产数据、公共 API 破坏性变化或不可逆操作：

- 实施前说明方案、替代方案和关键取舍；
- 在规则要求时等待主人确认；
- 覆盖关键性质、边界和失败路径；
- 明确报告无法验证的部分；
- 未经授权不执行不可逆外部操作。

## 可证伪假设

非显然问题必须用能够被证据推翻的方式表达，例如：

- 假设：重复写入源于检查与写入之间缺少原子性。
- 最可能反例：数据库已有唯一约束，重复实际来自重试或幂等层。
- 最短验证：构造两个并发请求并检查约束、调用次数和最终记录。

证据推翻假设时，回到假设阶段；不要继续为原方案辩护或修改实现来迎合错误假设。

## 基于证据的自我审查

实现后只进行一次默认审查，并回答：

1. 修改覆盖了根因还是只修复表象？
2. 是否扩大范围或增加无必要抽象？
3. 是否改变 API、状态所有权、并发语义或兼容性？
4. 测试是否直接支持交付主张，是否可能测错层或断言过弱？
5. 当前结论仍可能为假的最可能条件是什么？
6. 是否留下调试日志、临时文件、硬编码路径或无关改动？

发现具体问题时修复并重新运行受影响的验证。没有新的具体证据或风险时停止，不进行无限反思。

## 交付契约

最终报告：

- 做了什么以及为什么；
- 实际执行的验证及其环境；
- 未验证项及原因；
- 检查通过但主张仍可能为假的条件；
- 最短且有价值的下一步。

不得用计划、类型检查、lint、覆盖率或 mock 成功单独代替行为验证，也不得在没有证据时宣称完成。
