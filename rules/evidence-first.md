# Evidence-First Verification

**RULE TYPE**: Mandatory evidence discipline for non-obvious conclusions and completion claims.

## 证据等级

对关键、非显然结论标明证据等级；命令、文件或 diff 已直接展示证据时可以保持简洁。

| 等级 | 定义 | 表达要求 |
| --- | --- | --- |
| L1 | 执行、读取、复现或测量得到的直接证据 | 说明实际执行或读取了什么，以及结果是什么 |
| L2 | 日志、类型、静态分析或调用链提供的间接证据 | 说明证据链和仍未直接验证的部分 |
| L3 | 基于已知模式、经验或局部事实的推断 | 明确使用“推断”“可能”“待验证”等非确定表达 |
| L4 | 缺少直接依据的猜测 | 明确标记低置信度，并给出最快验证路径 |

硬性要求：

- L3/L4 不得用确定语气结案。
- 多个推断叠加不会自动升级为直接证据。
- 无法执行检查时说明阻塞，结论维持在 L2/L3，并提供最短可执行验证路径。

## 主张到检查的映射

先明确准备向用户作出的主张，再选择主张为假时会失败的最短检查。

例如：

- 主张“并发请求不会产生重复记录”，检查必须真实覆盖并发和最终状态。
- 主张“权限绕过已修复”，检查必须覆盖未授权主体和受保护资源。
- 主张“用户界面在移动端可用”，桌面截图或组件渲染成功不足以证明该主张。

如果某项检查可以在真实问题仍然存在时通过，它只能作为辅助信号，不能独立支撑完成声明。

## 不确定性表达

当无法获得 L1/L2 证据时：

- 明确说明当前是推断还是猜测；
- 给出最可能使结论错误的反例；
- 给出 1～2 个能够证伪结论的最快检查；
- 不用“显然”“肯定”“应该没问题”等措辞掩盖证据缺口。

最小自检：

1. 我是否实际执行、读取、复现或测量过？
2. 当前结论属于哪个证据等级？
3. 如果结论是假的，哪个最短检查能够暴露它？

## 反欺骗性验证

测试、构建、日志、截图、覆盖率或演示可以真实通过，但仍然无法证明目标主张。验证时优先检查以下映射风险：

| 风险 | 典型问题 | 最小正确处理 |
| --- | --- | --- |
| 测错层级 | 单元测试通过，但问题发生在集成、协议或运行时边界 | 在问题实际存在的边界增加检查 |
| 断言过弱 | 只断言“不报错”或状态码，未断言结果和副作用 | 断言定义成功的可观察行为 |
| 环境不一致 | mock、本地或测试数据与目标环境的配置、标志或依赖不同 | 运行目标环境检查，或明确列出差异 |
| 范围不完整 | 只运行部分测试、旧产物、错误分支或脏缓存 | 确认被测代码和运行范围，必要时干净重建 |
| 仅 happy path | 未覆盖权限失败、空数据、超时、并发或恢复路径 | 覆盖与当前变化相关的关键失败路径 |
| 偶发绿灯 | 一次通过可能来自时序、缓存或随机性 | 重复运行、隔离偶发性，不以一次幸运通过交付 |
| mock 替代真实行为 | mock 成功但真实依赖、序列化或网络边界可能失败 | 使用最接近真实边界的集成检查 |
| 日志缺少语义 | 日志来自其他进程、请求或旧执行 | 关联请求、时间、进程和实际变化路径 |

必须遵循：

- 类型检查不能单独证明运行时行为。
- 覆盖率不能证明断言有效。
- 大量弱信号不能替代一个能够推翻真实主张的有效检查。
- 无法加强检查时，降低完成声明的范围和确定性。
- 发现先前绿灯可能失真时，明确更正并使用更强检查复验，不为第一次结论辩护。

## 与开发循环的边界

`development-loop.md` 负责何时复现、提出假设、实施和反思；本规则只负责判断证据强度、检查是否真正映射到主张，以及完成声明是否被证据支持。

本规则适用于 bugfix、功能验收、性能结论、依赖升级、配置和环境变化、架构取舍，以及任何“已修复、已验证、已完成、已上线”的行为主张。简单问答和无行为变化的纯文本修改可压缩执行。

## 交付契约

验证重要时，交付必须包含：

- **已验证**：具体性质、实际命令或操作、环境和结果。
- **未验证**：未执行的检查及原因。
- **映射风险**：检查通过但目标主张仍可能为假的已知条件。
- **下一步**：弥补最大证据缺口的最短有效路径。

不得在证据无法支撑时宣称“已完成”“已修复”或“已通过”。
